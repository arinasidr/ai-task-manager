# Бенчмарк LLM

Общий скрипт для сравнения локальных моделей на эталонных запросах `cases.jsonl`.
Каждая модель получает **один и тот же** системный промпт (`prompts/system.md`), одинаковые
параметры генерации и одну JSON-схему ответа. Поле `expected` модели не передаётся:
по нему скрипт только проверяет ответ.

## Быстрый старт

```bash
ollama serve                      # если Ollama ещё не запущена
ollama pull qwen3:4b              # имена моделей здесь и ниже — примеры
python -m benchmarks.run --model qwen3:4b --machine ASUS
python -m benchmarks.compare      # таблицы по всем прогонам
```

Несколько моделей подряд, с одинаковыми настройками:

```bash
python -m benchmarks.run --model qwen3:4b --model gemma3:4b --model llama3.2:3b --machine ASUS
```

Адрес Ollama берётся из `ATM_OLLAMA_BASE_URL` (файл `.env`), по умолчанию `http://localhost:11434`.

## Параметры

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--model` | — | модель; можно указать несколько раз |
| `--machine` | — | метка компьютера (`ASUS`, `MacBook-M2`), чтобы не смешивать скорость разных машин |
| `--format` | `schema` | `schema` — ответ ограничен JSON-схемой (как будет в агенте); `json` — любой JSON; `none` — без ограничений, проверяет, умеет ли модель сама держать формат |
| `--think` | `off` | режим рассуждений для моделей, которые его поддерживают (`on` — сравнить качество с рассуждениями) |
| `--temperature`, `--seed` | `0`, `42` | детерминированная генерация |
| `--num-ctx` | `4096` | контекстное окно; промпт с самым длинным тестом занимает примерно 2–2,5 тыс. токенов |
| `--num-predict` | `1024` | максимум токенов ответа (обрезанные ответы видны как `truncated`) |
| `--repeats` | `1` | повторить каждый тест N раз и посчитать стабильность ответов |
| `--only`, `--category` | — | запустить часть тестов: `--only TEST_05,TEST_29`, `--category planning` |
| `--timeout` | `300` | таймаут одного запроса в секундах |
| `--no-warmup` | — | не делать прогревочный запрос (по умолчанию он отделяет время загрузки модели) |
| `--backend`, `--base-url` | `ollama` | `openai` — любой OpenAI-совместимый сервер (llama.cpp, vLLM), см. ниже |

## Что сохраняется

Для каждой модели создаётся папка `results/<дата-время>_<модель>/`:

- `meta.json` — модель, версия движка, размер и квантование, все настройки, SHA-256 промпта
  и файла тестов, сведения о компьютере, время загрузки модели;
- `responses.jsonl` — по каждому тесту: сырой ответ, разобранный JSON, ошибки схемы, все
  непройденные проверки с пояснением, задержка, число токенов и скорость;
- `summary.json` — сводные метрики.

Ответы пишутся сразу после каждого теста, поэтому при обрыве или Ctrl+C уже полученные
результаты не теряются. После трёх ошибок движка подряд прогон модели останавливается.

Папки с результатами коммитим в репозиторий: так оба участника видят прогоны друг друга,
а `compare` собирает общую таблицу.

## Как оценивается ответ

Проверяются только поля из `expected`, причём с учётом смысла поля:

| Поле | Правило |
|---|---|
| `intent`, `answer_status` | точное совпадение |
| `tasks` | число задач должно совпасть; задачи сопоставляются по названию в любом порядке; у каждой проверяются название (регистр, «ё/е», кавычки не важны, похожесть ≥ 0,8), приоритет и срок |
| срок (`deadline`) | дата сравнивается с датой, момент с моментом (`18:30+03:00` = `15:30Z`); добавленное время, потерянное время или время без смещения — ошибка |
| `dependencies` | связь «задача ← от чего зависит»; перепутанное направление — ошибка |
| `updates` | каждое ожидаемое изменение верно, и нет лишних изменений, о которых не просили |
| `task_ids`, `matching_tasks` | как множества; `ordered_task_ids` — с учётом порядка |
| `warnings`, `missing_fields` | ожидаемые коды должны быть, лишние допустимы |
| флаги подтверждения | точное совпадение, отсутствие поля — ошибка |

Дополнительно в каждом тесте проверяется, что модель не ссылается на ID задач, которых нет ни
в контексте, ни в запросе пользователя. Для `create_task` эта проверка не выполняется: при создании
исполнитель не читает поля с ID существующих задач, а модели часто нумеруют в них сами новые
задачи (`ordered_task_ids: [1, 2]`), что не является ссылкой на несуществующую задачу.

**Критичные ошибки** считаются отдельно, потому что для агента они опаснее остальных: действие
выполняется без нужного подтверждения (`requires_confirmation`, `should_execute`), выдуманы
задачи или ID задач.

## Метрики в summary.json

- `accuracy` — доля тестов, где пройдены все проверки (главная метрика качества);
- `mean_score` — средняя доля пройденных проверок (частичный зачёт);
- `by_category` — точность по категориям тестов;
- `critical_failures` — число критичных ошибок и их список;
- `json_strict_rate` — ответ сразу корректный JSON; `json_parsed_rate` — JSON удалось извлечь;
  `schema_valid_rate` — ответ соответствует схеме (следование формату);
- `latency_s` — задержка запроса: среднее, медиана, p90, максимум;
- `gen_tokens_per_s` — скорость генерации по счётчикам Ollama (без учёта загрузки модели и сети);
- `prompt_tokens_per_s` — служебное значение, в сравнение не входит: Ollama кэширует общий
  системный промпт и сообщает полное число токенов, но время только для необработанной части,
  поэтому скорость обработки промпта получается сильно завышенной;
- `warmup.load_s` — время загрузки модели в память; `memory` — сколько памяти она заняла;
- `consistency` (при `--repeats` > 1) — доля тестов с одинаковым вердиктом и одинаковым ответом.

Скорость сравниваем только в пределах одной машины, качество — между любыми прогонами
с одинаковыми промптом и тестами (`compare` предупредит, если хэши различаются).

## Пересчёт оценок

Правила проверки имеют версию (`SCORING_VERSION` в `scoring.py`), она записывается в
`summary.json`. Если правила или эталоны поменялись, модели заново запускать не нужно:

```bash
python -m benchmarks.rescore          # пересчитать все прогоны по сохранённым ответам
```

Сырые ответы, задержки и скорость сохраняются, пересчитываются только проверки и метрики.
`compare` предупредит, если в таблице смешаны прогоны с разными версиями правил.

История правил: v1 — первая версия; v2 — для `create_task` поля с ID существующих задач
не считаются выдуманными (после первого прогона на реальных моделях).

## Видеопамять и скорость

Перед прогоном модели бенчмарк выгружает из Ollama остальные загруженные модели, а после
прогона выгружает и её саму, чтобы каждая модель получала всю видеопамять. Колонка
«На GPU» в `compare` показывает, какая доля модели поместилась в видеопамять: если меньше
100%, часть слоёв считалась на процессоре и скорость занижена. Во время замеров лучше закрыть
браузер, видео и игры — они тоже занимают видеопамять.

## Другие движки (P04)

Тот же набор тестов можно прогнать через llama.cpp или vLLM — оба поднимают OpenAI-совместимый
сервер:

```bash
llama-server -m model.gguf --port 8080
python -m benchmarks.run --backend openai --base-url http://localhost:8080/v1 --model local --machine ASUS --tag llamacpp
```

Если сервер не возвращает `timings`, как llama.cpp, скорость генерации оценивается по общему
времени ответа и помечается `tps_estimated`.

## Изменение промпта и тестов

Промпт — общий контракт для всех моделей. Если его меняем, перезапускаем все сравниваемые модели:
результаты с разными хэшами промпта несопоставимы. Новый тест достаточно добавить строкой в
`cases.jsonl`; тест `tests/test_benchmark_scoring.py` проверит, что эталон проходит собственную
проверку и укладывается в схему ответа.
