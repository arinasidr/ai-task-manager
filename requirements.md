# Техническое задание - AI Task Manager

## 1. Назначение и цель
**AI Task Manager** - мультиагентная система для управления личными задачами на русском языке посредством запросов на естественном, разговорном языке. Она позволяет создавать, просматривать, редактировать, завершать и удалять задачи, а также строить простые зависимости, рекомендовать порядок выполнения и сохранять подтвержденные предпочтения пользователя.

**Учебная цель**: создать мультиагентную систему на базе LLM, в которой применяются маршрутизация моделей, независимая валидация, инструменты, скиллы, несколько слоев памяти, изоляция среды выполнения, Evals и Observability. Сама работа должна сопровождаться понятной документацией и воспроизводимыми экспериментами. 

**Целевой пользователь**: один человек со своим списком задач. Аккаунты, командное взаимодействие в MVP не входят.

## 2. Границы MVP и правила продукта

### 2.1. Функции, которые реализуем

1. Создание одной или нескольких задач из текстового сообщения.
2. Просмотр списка, деталей и актуальных статусов задач.
3. Изменение существующей задачи по явному ID.
4. Перевод задачи в работу и завершение задачи по ID.
5. Удаление задач по ID с подтверждением.
6. Хранение срока без даты, даты без времени или полного срока (дата, время, часовой пояс).
7. Хранение явно заданного приоритета и выдача отдельных рекомендаций, если он не задан.
8. Зависимости типа: «сначала А, затем Б», проверка циклов, учёт зависимости в рекомендациях.
9. Рекомендация порядка задач с коротким обоснованием, без почасового расписания.
10. Рабочая, краткосрочная и долгосрочная память, включая гибридное сохранение предпочтений.
11. Подтверждение опасных действий, независимая валидация предложенных планов, сообщения о длительной проверке.
12. Работа через HTTP API, Swagger и терминальный клиент (CLI).

### 2.2. Фиксированные продуктовые решения

| Тема | Согласованное правило |
|---|---|
| Язык | Русский в MVP |
| Статусы | `todo`, `in_progress`, `done` |
| Приоритеты | `low`, `medium`, `high`, допускается `null`, если не указан |
| Поля | Название, необязательные описание, срок и приоритет, статус, зависимости, служебные ID и timestamps |
| Удаление | Физическое, только после подтверждения |
| Дубликаты названий | Разрешены, различаются ID |
| Относительные даты | Вычисляются относительно локальных даты/времени пользователя, неоднозначные уточняются |
| Часовой пояс по умолчанию | Из устройства клиента / явно указанный в запросе имеет приоритет |
| Ссылка на существующую задачу | Для изменения/завершения/удаления всегда требуется ID; местоимения без ID сами не исполняются |
| Несогласованные сроки и зависимости | Предупреждаем, сроки самовольно не меняем |
| Обычные операции | Создание и однозначное одиночное изменение с ID — без отдельного подтверждения |
| Опасные операции | Удаление, массовые изменения, завершение вопреки невыполненной зависимости — с подтверждением |
| Планирование | Предлагаем порядок с обоснованием, без расписания по часам |
| Предпочтения | Ограниченный набор: удобное время работы, рабочие дни, предпочтительные типы задач |
| Долгая валидация | После двух отклонений сообщаем, что проверка затянулась, и продолжаем исправление; предусмотрены отмена и технический таймаут |
| Действия при ошибке | Непроверенное действие не должно записываться в БД; пользователь получает статус/ошибку |

## 3. Функциональные требования

| ID | Требование | Детализация |
|---|---|---|
| FR-01 | Создание одной задачи | Из запроса извлекаются название, необязательное описание, срок, явный приоритет; данные сохраняются после проверки. |
| FR-02 | Создание нескольких задач | Из одного сообщения создаётся ровно указанное число задач, без добавления вымышленных пунктов. |
| FR-03 | Просмотр | Список/детали читаются из актуальной БД, не восстанавливаются исключительно из памяти LLM. |
| FR-04 | Изменение задачи | Для изменения существующей записи пользователь сообщает ID. Без ID агент предлагает список подходящих записей с ID и просит выбрать. |
| FR-05 | Статусы | Допустимы только `todo`, `in_progress`, `done`. Переходы по просьбе пользователя, без скрытой смены статуса. |
| FR-06 | Завершение с зависимостями | При невыполненных предшественниках предупреждаем и запрашиваем подтверждение, а остальные задачи не завершаются автоматически. |
| FR-07 | Удаление | Перед физическим удалением показываем выбранный ID и затрагиваемые связи, запрашиваем подтверждение. |
| FR-08 | Удаление связанной задачи | Удаляется только выбранная задача и все её входящие/исходящие связи, а остальные задачи и связи между ними сохраняются. |
| FR-09 | Зависимости | Поддерживаются направленные связи-предшественники, циклические и несуществующие ссылки запрещаются кодом. |
| FR-10 | Сроки | Поддерживаются отсутствие срока, только дата либо дата+время+часовой пояс, без выдумывания отсутствующего времени. |
| FR-11 | Относительные даты | «Завтра», «через три дня» вычисляются с учётом локальной даты пользователя. Неоднозначность ведёт к вопросу, а не к записи. |
| FR-12 | Часовой пояс | Клиент передаёт таймзону устройства в IANA-формате, явная зона в сообщении переопределяет её для этого срока. |
| FR-13 | Приоритет | Явно заданный записывается, а при отсутствии хранится `null`, при планировании показывается `recommended_priority`, не записываемый без согласия. |
| FR-14 | Рекомендация | Планировщик предлагает порядок, учитывает дедлайны, предшественников, явно заданные приоритеты и подтверждённые предпочтения и кратко объясняет свое предложение. |
| FR-15 | Конфликт сроков | Обнаружив противоречие, предупреждает и предлагает возможное решение, но не переносит срок автоматически. |
| FR-16 | Идентификация задачи | Не разрешает «перенеси её»/«закрой отчёт» без ID при операции изменения, а предлагает варианты с ID. |
| FR-17 | Предпочтения | Явные предпочтения сохраняются, а автоматически обнаруженные предъявляются на отдельное подтверждение. |
| FR-18 | Обновление памяти | Подтверждённые предпочтения можно просмотреть, изменить и удалить, а устаревшие значения не используются как актуальные. |
| FR-19 | Валидация | Валидатор из другого семейства LLM проверяет план до воздействия на БД, а результат проверки и причины отклонения записываются. |
| FR-20 | Продолжительная валидация | После двух отклонений пользователь видит сообщение о задержке и возможность отменить запрос, а система продолжает корректировку, пока не получит успех либо пока не наступят технический таймаут/отмена. |
| FR-21 | Инструменты | Только явно разрешённые операции чтения/записи, а параметры, существование IDs, зависимости и подтверждения проверяются обычным кодом. |
| FR-22 | Интерфейсы | Одинаковые правила доступны из HTTP API и CLI, Swagger для ручной проверки. |
| FR-23 | Защита от повторной записи | Повторная проверка валидатором или повторное получение ответа не создаёт дублирующие операции, а запись происходит после проверки и подтверждения ровно один раз. |

### 3.1. Политика сроков и часовых поясов

- **Нет срока:** все поля дедлайна `null`.
- **Есть только дата:** сохраняем `due_date`, `due_time = null`, `due_at_utc = null`.
- **Есть дата и точное время:** нормализуем момент в UTC и сохраняем исходную зону IANA для обратного отображения.
- **Приоритет определения часового пояса:** зона, явно сказанная пользователем > зона устройства, присланная клиентом. Если часовой пояс не определён, а для операции необходим точный момент, задаём уточняющий вопрос.
- **Swagger/ручной HTTP-запрос:** сервер не может надёжно узнать зону устройства без данных клиента; поэтому поле часового пояса передаётся явно. Скрыто использовать серверную таймзону запрещено.
- **Относительные даты:** используем локальные дату и время, актуальные на начало обработки сообщения, а не время, когда LLM завершила генерацию.
- **Неоднозначные выражения** («как-нибудь к выходным», конфликтующая дата, неоднозначное время при переходе на летнее/зимнее время) — уточняем.

Рекомендуемое представление: `due_date` (`YYYY-MM-DD` или `null`), `due_time` (`HH:MM` или `null`), `due_timezone` (IANA или `null`), `due_at_utc` (UTC ISO 8601 или `null`).

### 3.2. Политика приоритетов

- Допустимые уровни: `low`, `medium`, `high`. Неуказанный приоритет — `null`, а не неявно «средний».
- Запрос «сделай это важным/срочным» интерпретируется по явно согласованным правилам маппинга на `high`, а сомнительные формулировки уточняются.
- Планировщик может вернуть `recommended_priority` с причиной. 
- При принятии предложения пользователем запись обновляется по ID.

### 3.3. Политика зависимостей и удаления

Пусть **В от А** означает: A нужно закончить перед B.

- Создание связи с несуществующим ID и циклической зависимости запрещено.
- Если пользователь завершает B, пока A не завершена, агент перечисляет невыполненные предшественники и запрашивает подтверждение. После подтверждения меняется только B.
- При удалении A выполняется транзакция: физически удалить A и ссылки на A. Если есть цепочка C от В от А, связь С от В и сами B/C сохраняются.
- Удаление и связанные операции показывают, что именно изменится, до подтверждения. Отказ не меняет БД.
- Если одна операция затрагивает несколько задач, требуется подтверждение даже при отсутствии зависимостей.

### 3.5. Подтверждения и статусы длительной проверки

1. Сначала агенты готовят структурированный план действий, а валидатор оценивает его.
2. Код валидирует схему плана и бизнес-правила, только после этого выполняются разрешённые операции.
3. Удаление, массовое изменение и завершение вопреки зависимости создают ожидающее подтверждения действие с описанием затрагиваемых IDs и изменений.
4. Пока подтверждение не получено, записей в БД нет. Отмена оставляет данные прежними.
5. При двух последовательных отклонениях плана валидатором пользователь получает промежуточный статус: «Проверка занимает больше времени, продолжаю исправлять план. Можно отменить».
6. Новые исправленные варианты могут проверяться снова без заранее установленного ограничения числа попыток. Однако у выполнения есть настраиваемый технический таймаут и явная отмена пользователем, а при остановке непринятый план не записывается.
7. Повторная проверка не повторяет уже сделанные изменения: запись производится единожды после валидации. Способ доставки промежуточного статуса (поток событий или опрос состояния запроса) фиксируется при проектировании API.

**Риск выбранной политики:** повторные попытки LLM могут привести к длительной обработке и расходу ресурсов/API-токенов. Технический таймаут обязателен для устойчивого MVP. Перед настройкой его значения измеряем типичную длительность inference на наших ноутбуках.

## 4. Сущности и минимальная модель данных

### Task

| Поле | Тип/смысл |
|---|---|
| `id` | Уникальный ID задачи |
| `title` | Обязательная непустая строка |
| `description` | Необязательный текст |
| `status` | `todo` / `in_progress` / `done` |
| `priority` | `low` / `medium` / `high` / `null` |
| `due_date` | Локальная дата / `null` |
| `due_time` | Локальное время / `null` |
| `due_timezone` | IANA timezone / `null` |
| `due_at_utc` | Абсолютный момент / `null` |
| `created_at`, `updated_at` | Технические метки времени |

**TaskDependency:** `predecessor_task_id`, `successor_task_id`, целостность ссылок обеспечивается БД и кодом, циклы дополнительно проверяются кодом.

**Preference:** `id`, `kind`, `value`, `status` (`proposed`/`confirmed`), `source` (`explicit`/`inferred`), `created_at`, `updated_at`. Разрешённые `kind`: удобное время работы, рабочие дни, предпочтительные типы задач. «Типы задач» в предпочтениях **не означают**, что у Task обязательно есть отдельное поле категории.

**Conversation/Agent State:** `conversation_id`, рабочие сообщения/контекст, промежуточный план и статус выполнения.

**PendingAction:** `action_id`, тип операции, затрагиваемые IDs, подготовленные изменения, статус `pending/confirmed/cancelled/expired`, срок действия. После подтверждения ещё раз проверяются права и актуальность данных.

**Execution/Observability:** `run_id`, trace ID, этапы агентов, выбранная модель, ошибки, длительность, число отклонений/повторов; чувствительные данные в логах ограничиваются.

## 5. Мультиагентная архитектура

**Три логические агентные роли в единой системе:**

| Роль | Назначение | Выход |
|---|---|---|
| **Аналитик** | Распознаёт намерение, сущности, текст задач, сроки, ID, запрос на уточнение | Структурированный разбор запроса |
| **Планировщик** | Читает актуальные задачи, строит допустимый план действий/порядок выполнения | План операций и рекомендации |
| **Валидатор** | Независимо проверяет план на соответствие запросу, корректность ссылок и противоречия | Решение `accept/reject` и причины/замечания |

Агенты не являются тремя независимыми чат-ботами: они работают в одном управляемом workflow и обмениваются общим структурированным состоянием. Валидатор должен использовать LLM **другого семейства** относительно проверяемой модели.

**Последовательность:** пользователь пишет запрос, его принимает  аналитик и при необходимости запрашивает уточнения, далее планировщик с доступом к разрешённым Tools чтения, далее валидатор, при отклонении исправление, после детерминированная проверка, подтверждение опасных действий и разрешённые Tools записи, только потом ответ.

**Не делаем LLM-агента для CRUD только ради количества:** сохранение в БД выполняет обычный проверяемый Python-код. Три агентные роли — предварительная архитектура. 

## 6. Tools, Skills и файлы контекста

**Минимальные инструменты:**
- `list_tasks`, `get_task` — получение актуальных записей.
- `create_task`, `update_task`, `change_task_status`, `delete_task` — контролируемые операции.
- `get_dependencies`, `add_dependency`, `remove_dependency` — связи задач.
- `get_preferences`, `propose_preference`, `confirm_preference`, `update_preference` — память, если это обосновано архитектурой.

Каждый инструмент имеет строгую схему параметров, ограничения и обработку ошибок. Опасные вызовы требуют проверенного токена/ID подтверждения на стороне приложения.

**Собственные Skills:** минимум `task-extraction`, `task-planning`, `task-validation`, реализованные как содержательные Markdown-файлы с назначением, применимостью, инструкциями и примерами.

## 7. Память

| Уровень | Назначение | Правила |
|---|---|---|
| Рабочая | Состояние текущего исполнения графа, выбранная модель, план, промежуточные проверки | Не путать с постоянным списком задач |
| Краткосрочная | Контекст диалога, состояние ожидания подтверждения, продолжение запроса | Восстанавливается внутри текущего `conversation_id` |
| Долгосрочная | Подтверждённые предпочтения пользователя и их актуальная версия | Сохраняется между сессиями, поддерживает просмотр/изменение/удаление |

**Гибридное сохранение:**
- Явная просьба «запомни, что...» сохраняет разрешённый тип предпочтения.
- Автоматически обнаруженное предпочтение записывается только как предложение и **не применяется до подтверждения**.
- Более позднее явное изменение актуализирует факт; конфликтующие старые значения перестают участвовать в планировании.
- Удаление предпочтения исключает дальнейшее применение этого факта.

## 8. Интерфейсы

**Обязательны:**
1. HTTP API на FastAPI.
2. Swagger/OpenAPI.
3. CLI, который обращается **к API**, не к БД и не напрямую к LangGraph.

**Предварительный контракт API (может уточняться без нарушения пользовательских сценариев):**

| Маршрут | Назначение |
|---|---|
| `POST /api/v1/chat` | Отправить сообщение, `conversation_id` и `client_timezone`; вернуть ответ или `run_id` |
| `GET /api/v1/tasks` | Получить актуальные задачи |
| `GET /api/v1/tasks/{id}` | Получить детали |
| `POST /api/v1/actions/{id}/confirm` | Подтвердить ожидающее действие |
| `POST /api/v1/actions/{id}/cancel` | Отменить действие |
| `GET /api/v1/runs/{id}` | Получить ход/статус длительного запроса, включая уведомление о затянувшейся проверке |
| `POST /api/v1/runs/{id}/cancel` | Отменить длительную обработку |
| `GET /api/v1/preferences` | Просмотреть подтверждённые предпочтения |

Если запрос занимает длительное время, **клиент должен видеть промежуточный статус до завершения**. Можно применить polling или streaming; реализация определяется при проектировании и фиксируется в OpenAPI.

## 9. Критерии приёмки

| ID | Проверка | Успешный результат |
|---|---|---|
| AC-01 | «Создай две задачи...» | Созданы ровно две задачи, нет добавленных LLM задач. |
| AC-02 | «Подготовь отчёт» | Создана задача без срока и без произвольно назначенного приоритета. |
| AC-03 | «Подготовь отчёт до 20 октября» | `due_date` заполнено, `due_time = null`, `due_at_utc = null`. |
| AC-04 | «Подготовь отчёт 20 октября в 18:30 по Москве» | После сохранения и чтения показаны 18:30 и `Europe/Moscow`, хранение момента в UTC корректно. |
| AC-05 | «Создай ... завтра» в заданном часовом поясе | Используется локальная дата пользователя; неоднозначность вызывает уточнение. |
| AC-06 | Приоритет явно указан | В БД сохраняется один из `low/medium/high`. |
| AC-07 | Приоритет не указан | В БД `priority = null`; предложение планировщика показывается отдельно. |
| AC-08 | Две задачи с одним названием | Обе допустимы, ID различаются. |
| AC-09 | «Перенеси её на завтра» без ID | Данные **не изменены**, возвращён запрос ID/варианты задач с ID. |
| AC-10 | Изменение с правильным ID | Изменяется только выбранная задача; остальные не тронуты. |
| AC-11 | Цепочка A → B → C | Сохраняются корректные зависимости, попытка добавить C → A отклоняется. |
| AC-12 | Завершить B, если A не сделана | До подтверждения изменения нет; после подтверждения меняется только B. |
| AC-13 | Отказ от завершения вопреки зависимости | Статусы остаются прежними. |
| AC-14 | Удалить A в цепочке A → B → C | Без подтверждения ничего; после подтверждения удаляется только A и ссылка A → B, B → C сохраняется. |
| AC-15 | Удалить задачу | Запись физически отсутствует в БД; автоматического восстановления нет. |
| AC-16 | Конфликт срока и зависимости | Показано предупреждение; сроки автоматически не исправлены. |
| AC-17 | Планирование | Есть рекомендуемый порядок задач и краткая причина; почасовое расписание не требуется. |
| AC-18 | Явное сохранение предпочтения | Предпочтение применяется в новой сессии. |
| AC-19 | Автоматически обнаруженное предпочтение | До подтверждения не влияет на планирование; после подтверждения может учитываться. |
| AC-20 | Изменение/удаление предпочтения | Устаревший факт более не используется как актуальный. |
| AC-21 | Валидатор дважды отклоняет план | Пользователь получает сообщение о задержке; запускается следующая корректировка без записи в БД. |
| AC-22 | Пользователь отменяет долгую проверку / истекает таймаут | Обработка останавливается, непроверенные изменения в БД не появляются. |
| AC-23 | Подтверждение опасной операции | Показаны IDs и изменения; отказ оставляет БД неизменной. |
| AC-24 | Полный агентный workflow | В трейсе видны роли аналитика, планировщика, валидатора, модель и Tool-вызовы. |
| AC-25 | Независимая валидация | Валидатор использует LLM другого семейства, ошибки плана фиксируются. |
| AC-26 | Наблюдаемость | Для контрольного запроса доступны лог, метрики, trace/trajectory и сработавший тестовый алерт. |
| AC-27 | Воспроизводимость | Запуск по README и Evals на согласованном окружении воспроизводится. |
| AC-28 | Изоляция | Запрещённое обращение к ресурсам хоста блокируется и фиксируется в проверке. |

Тест-кейсы должны включать нормальные, неоднозначные, конфликтные, повторные и потенциально опасные запросы, а также простые попытки prompt injection в пользовательском тексте.
