# Оценка AI Task Manager

## Как проводились прогоны

Набор содержит 28 сценариев: создание и изменение задач, сроки, приоритеты, зависимости, планирование и подтверждение удаления. Для каждого сценария создаётся отдельная временная SQLite-база с заданными задачами. Запрос обрабатывает рабочий граф с локальными моделями; дата и часовой пояс зафиксированы в сценарии.

Оценщик сопоставляет намерение и извлечённые данные с эталоном, проверяет порядок задач и сравнивает состояние БД до и после действия. Сценарии удаления дополнительно проверяют, что задача остаётся в БД до ответа пользователя.

```bash
.venv/bin/python -m evals.batch --only EVAL_017
.venv/bin/python -m evals.summary
.venv/bin/pytest -q tests/test_evals_scoring.py
```

`batch` записывает каждый результат в `evals/results/*.jsonl`. `summary` повторно применяет текущие правила оценки к сохранённым ответам и не вызывает модели. Список файлов для сводки находится в `SOURCES` файла `evals/summary.py`: после нового прогона его нужно обновить. Время `duration_seconds` измеряет только обработку сообщения в `run_chat`, без подготовки БД, подтверждения действия и оценки судьёй.

## Разбор ошибок

Не прошли EVAL_002, EVAL_007, EVAL_012, EVAL_013, EVAL_107 и EVAL_017. EVAL_002 и EVAL_007 содержат формулировки, которые можно трактовать неоднозначно; поэтому дополнительно запущены явные варианты EVAL_017 и EVAL_018. В EVAL_017 аналитик извлёк данные правильно, но валидатор отклонил корректный план по неверным основаниям. В EVAL_018 явная цепочка зависимостей была создана успешно. EVAL_012 показал потерю низкого приоритета, EVAL_013 — лишнее изменение статуса и ложный отказ валидатора, EVAL_107 — выбор списка задач вместо плана и пропуск просрочки.

## LLM-as-a-Judge

Десять сохранённых планов (EVAL_101–EVAL_110) сначала оценены вручную по пяти критериям из `judge_rubric.md`: полнота, порядок, ограничения, объяснение и аккуратность. Затем те же ответы оценили Phi4-mini и Ministral-3. Эталонные ответы, оценки человека и результаты проверки кодом не передавались судье.

При одинаковой рубрике среднее абсолютное расхождение с ручной оценкой составило 5,1 балла из 10 для Phi4-mini и 1,3 балла для Ministral-3. Полное совпадение было в 1/10 и 5/10 случаев соответственно. Первый прогон Phi с другой начальной формулировкой рубрики сохранён как пилотный. Оба судьи допускали фактические ошибки в объяснениях: например, Phi дал 10/10 случаю EVAL_107 без плана. Поэтому баллы LLM дополняют, но не заменяют проверки состава задач, зависимостей и состояния БД.

В рабочем графе Ministral-3 также назначен валидатором. Для этих десяти запросов планирования валидатор выполнял проверки кодом и не вызывал модель: план не менял данные. Это делает сравнение планов с ответами Gemma отдельным, но не превращает Ministral в независимого внешнего судью всей системы.

## Связь с observability

Офлайн-оценка хранит входные сценарии и результаты в JSONL. Работающий FastAPI считает число запросов к `/api/v1/chat`, суммарную длительность, ошибки агентов, повторы и алерты; показатели доступны через `/api/v1/metrics`. Сообщения о запросах пишутся в лог Uvicorn. Алерт возникает при трёх ошибках одного агента за пять минут. Сейчас показатели и алерты хранятся в памяти процесса и сбрасываются при перезапуске.

Трейсы моделей и инструментов пишутся в Phoenix: по ним видно путь конкретного запроса, длительность каждого шага, передачи между агентами и причины повторов. Непрерывный сбор ресурсных метрик и автоматический периодический запуск eval-набора пока не настроены.

## Ограничения интерпретации

Результаты относятся к конкретным сохранённым прогонам локальных моделей. Даже при фиксированных параметрах генерации повторный прогон может дать другой ответ; для сравнения с ручной оценкой используются одни и те же сохранённые ответы. В ручной строке EVAL_107 оценка `restraint = 0` расходится с текстом рубрики, поскольку в ответе нет выдуманных фактов. Исходная разметка сохранена без исправления после просмотра оценок судей; это расхождение учитывается при интерпретации их согласия.
